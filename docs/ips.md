# The IPS page

MikroDash can classify the traffic a MikroTik forwards with
[nDPI](https://github.com/ntop/nDPI) and act on it: log a flow, block the server
it reached, or quarantine the client that made it. The page is **Security -> IPS**.

```
router  mangle action=sniff-tzsp: the first bytes of each forwarded connection
   |    UDP 37008, TZSP
   v
mikrodash-dpi (a container on the router): nDPI, one JSON line per flow
   ^    TCP 37009, "HELLO <token>"
   |
MikroDash: the rules -> address lists -> raw drop rules on the router
```

## What it is, and what it is not

- **Detect, then block.** RouterOS forwards a packet whatever the sensor thinks of
  it, so this cannot be an inline IPS. A verdict becomes an address-list entry with
  a timeout, which raw rules drop. The first packets of the flow that was judged
  have already passed; the rest of that connection, and every later one, are
  dropped.
- **Blocking is by address.** `block` lists the server for every client; a service
  on a shared CDN takes its neighbours with it. `quarantine` lists the client, the
  precise answer to "this device should not be doing that".
- **IPv4.** The mangle rule copies IPv4, and the lists are IPv4 lists.
- **Fasttrack hides traffic.** A fasttracked connection leaves the mangle table
  after its first packets, often before the TLS ClientHello that names the service.
  The Setup tab's Preview warns and gives the change:
  `/ip/firewall/filter/set [find where action=fasttrack-connection] connection-bytes=20000-0`.
- **The first bytes, or every packet.** Setup's *Inspection* copies the first
  20000 bytes of each connection by default, which is what nDPI names a service
  from. *Every packet (heavy)* drops the `connection-bytes` limit: the router sends
  its whole forwarded throughput a second time and the sensor inspects all of it.
  It is for routers sized for it; the Setup screen, Preview and Apply all say so,
  and with it any fasttrack rule must be disabled, not just delayed.

## Setting it up

1. **Containers.** Install the `container` package and, once, with physical access:
   `/system/device-mode/update container=yes`, then press the reset button or
   power-cycle. An external disk (`usb1`) is recommended.
2. **Setup tab: the sensor.** Choose where the container lives, the disk, and the
   addresses that must never be listed (your workstation, servers, resolvers). The
   router, MikroDash and the sensor are always protected. Leave **Enforce** off to
   start with.
   - **Network** lists the router's networks. A bridge's own network is joined as a
     port of that bridge; a VLAN on a VLAN-filtering bridge as a port of that bridge
     with the VLAN as its `pvid`. A network that cannot be joined (a physical port, a
     VLAN on a bridge that does not filter) is listed, greyed, with the reason.
   - **Address by DHCP** leaves the address to that network's DHCP server. MikroDash
     reads the lease off the veth (`dhcp-address` in `/interface/veth/print`) before
     every connection. Reserve it on the DHCP server by the veth's `mac-address`, or
     press Apply again when it changes: the mangle rule copies to the address it was
     applied with.
   - **Or a fixed address**: one in the chosen network, or in any of the router's
     networks when none is chosen; any other address is the second of a /30 of its
     own (`172.31.255.2`), with a bridge and the router's address on it.
3. **Show the commands**, and run them in the router's terminal. They create the
   veth, its bridge port (and, on a /30, the bridge and the router's address) and
   the container, with the token MikroDash will send. The image is `ghcr.io/jenubis78/mikrodash-dpi`, built
   by `.github/workflows/dpi-sensor.yml` on a `dpi-v*` tag.
4. **MikroDash must reach the sensor** at its address on TCP 37009. When MikroDash's
   host routes through this router, that works as it is. The header turns to
   `sensor up`.
5. **Preview, then Apply** writes one mangle rule and three raw rules, each
   commented `MikroDash IPS`. Remove takes them off and empties the two lists.
6. **Rules tab.** Start with `log` rules and read **Decisions**; the Applications tab
   lists the names nDPI uses, and the rule editor picks applications, categories, breeds
   and risks from lists printed from the sensor's own nDPI (`internal/ips/ndpi_catalog.json`,
   regenerated by `dpi-sensor/tools/catalog.c`). When the decisions are what you want, turn **Enforce**
   on.

## Geofencing

Two ways, and they combine:

- **A rule criterion.** A rule's **Countries** match the flow's party on the internet
  (where it went, or where it came from when it came in), from the geo database. It
  needs the sensor, and acts per flow like any other criterion.
- **Country lists on the router (Geo tab).** Two lists and a mode:
  - **Whitelist**: countries never dropped. Until a choice is saved it holds the
    router's own country (its WAN address's, or the place set for it).
  - **Blacklist**: countries dropped in *Block the blacklist* mode, less any the
    whitelist names. Their IPv4 networks, merged, go into `mikrodash-ips-geo`.
  - *Allow only the whitelist* drops every other country instead: the whitelist's
    networks and the private ranges go into `mikrodash-ips-geo-allow`, and the
    rules match what is **not** on it (`src-address-list=!mikrodash-ips-geo-allow`).

  Filter rules commented `MikroDash IPS: geo` drop **new** connections from those
  countries (inbound: `forward` and `input`), to them (outbound: `forward`), or
  both. Replies to connections already open are left alone. No sensor is needed.

The apply runs in the background, one API write per prefix, and the tab shows its
progress. The list is filled before the rules go in, and the rules come out before it
is emptied. Re-applying (after a geo database update, or a new choice) writes only the
difference, and switching mode fills the new list before the rules move and empties
the old one after. More than 100000 networks is refused, and so is an inbound choice
that would cut off the router's own public address or an address someone is logged
in to it from now - MikroDash included: a blacklist holding it, or a whitelist
leaving it out.

## Safety

- Every listing is judged by `guard.CheckIPSTarget`, which refuses the router's own
  addresses, the addresses the router sees MikroDash from, the sensor, your
  protected list and special addresses, and refuses everything while the router's
  addresses cannot be read.
- At most sixty listings a minute per router; past that, decisions are recorded as
  `limited`.
- Every entry times out on its own (one minute to a week).
- Rule, sensor and router changes are for administrators, and are audited.
